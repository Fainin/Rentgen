# Rentgen — Stencil Implementation (decision delta)

This skill is an **implementation decision delta**, not a spec rewrite. The
source of truth stays where it has always been:

- `CLAUDE.md` (repo root) — operational summary and conventions.
- `docs/specs/2026-07-18-rentgen-sdk-design.md` — the SDK-first design and
  runbook.
- `docs/specs/workstreams/README.md` — the frozen seam registry and
  ownership map.

Those specs currently name **Lit** as the widget technology. The agreed
implementation choice, recorded here, is **Stencil** for the generated
Angular and React wrappers and for the Angular ControlValueAccessor (CVA)
configuration. Raw Custom Elements remain the portable baseline that every
wrapper targets. **Angular SSR parity is not a documented Stencil
output-target guarantee** and must not be claimed.

Read this file before writing or modifying any Rentgen widget, wrapper, or
output-target config. When this file and a source spec disagree, the source
spec wins for contracts and ownership; this file wins only for the
implementation technology choice.

## Purpose and source-of-truth

This skill exists so a single, checkable reference holds the Lit-to-Stencil
decision and the rules that follow from it. It does not introduce new tags,
events, CSS variables, factory signatures, package configuration, or fainin
version facts. Anything not listed here is unchanged from the source specs.

Authoritative inputs, in priority order:

1. `docs/specs/2026-07-18-rentgen-sdk-design.md` — architecture, data flow,
   build order, risks.
2. `docs/specs/workstreams/README.md` — ownership map, frozen seam registry,
   golden rules, scope guardrail.
3. `CLAUDE.md` — conventions, commands, current state.

This file adds one decision on top: widgets ship as Stencil components, with
framework wrappers generated by Stencil output targets. Nothing else in those
three documents is overridden.

## Architectural delta — Lit to Stencil

The design doc and `CLAUDE.md` describe the widgets as Lit custom elements.
The implementation choice recorded here replaces that with Stencil, for these
reasons and only these reasons:

- Stencil's output targets generate first-class **Angular** and **React**
  wrappers from one component source, which is the multi-framework
  distribution story the design doc already asks for.
- Stencil's Angular output target supports **CVA configuration** for
  form-associated widgets, which Lit would require hand-wiring.
- Raw Custom Elements stay the portable baseline. A host app that just wants
  `<rentgen-scanner>` in plain HTML still gets it; the wrappers are opt-in.

What does **not** change:

- The SDK-first, client-side-only, no-backend posture.
- The adapter plugin surface and the `detect → enrich → price → total` value
  chain.
- The frozen tags, events, CSS variables, client API, and factory signatures
  listed below.
- The Phase 1 → 2 → 3 firewall.
- Workstream ownership and the scope guardrail.

The specs' mention of Lit is treated as the illustrative technology choice at
drafting time. This skill is the approved replacement for the implementation
only.

## SDK/host boundaries

- `packages/sdk` owns the widgets, their Stencil source, and the generated
  wrapper packages. Host apps consume wrappers or raw Custom Elements; they
  do not import Stencil internals.
- `apps/app` is a **Vite SPA**. It calls `configureRentgen()` and mounts the
  widgets. It does not run server-side rendering.
- The SDK never reads `import.meta.env`. Host apps pass `VITE_*` values into
  `configureRentgen`. This stays exactly as `CLAUDE.md` states.
- Adding a data source still means "write an adapter, register it" — no
  widget or app changes. Stencil does not alter this.

## Stencil component rules

- One component per tag. Tags are frozen: `rentgen-scanner`,
  `rentgen-results`, `rentgen-upsell`.
- Each widget **self-registers** on import and **never imports another
  widget**. Cross-widget coordination goes through the `events.ts` bus only.
- Use Shadow DOM for style encapsulation. Theme exclusively through the
  frozen CSS custom properties; never reach into internals.
- TypeScript strict. Immutable state updates. Small, focused files
  (200–400 lines), organized by domain.
- Adapters throw on API failure; widgets surface it via the `scan:error`
  event. Never silently swallow.
- Public methods on a widget must be `async` (Stencil `@Method()` rule).
- Do not add new tags, events, CSS variables, factory signatures, or
  package configuration. If a task seems to require one, stop and follow the
  scope guardrail below.

## Properties and events

Use typed `@Prop()` members for the public element API and `@State()` only for
internal render state. Primitives may be supplied as attributes; objects and
arrays are JavaScript properties and must not be serialized into attributes.
Public, user-driven events must be typed DOM `CustomEvent`s that cross Shadow
DOM (`bubbles: true`, `composed: true`) before a framework wrapper maps them.

Frozen event bus (`packages/sdk/src/events.ts`, owned by Stream 4):

- `scan:start` `{}` — a scan began; show a spinner.
- `scan:complete` `ScanResult` — a scan finished; results and upsell render
  from this.
- `scan:error` `{ message: string }` — surface the error.

Frozen custom-element tags:

- `rentgen-scanner` (Stream 1)
- `rentgen-results` (Stream 4)
- `rentgen-upsell` (Stream 5)

Frozen client API:

- `getClient().scan(imageBase64) → Promise<ScanResult>`
- `getClient().consume(sessionId) → Session | null`
- `configureRentgen(config)`

Frozen factory seams:

- `createDetectionAdapter(config): DetectionAdapter`
- `createEnrichmentAdapter(config): EnrichmentAdapter`
- `createAssetAdapter(config?): AssetAdapter`

When mapping these to Stencil: events become `@Event()` emitters typed to the
frozen payloads; tags become `@Component({ tag: ... })`; client API calls
happen inside component methods, not on the host. Do not rename anything.

## Theme

Frozen CSS custom properties:

- `--rentgen-accent`
- `--rentgen-card-bg`
- `--rentgen-radius`
- `--rentgen-font`

Need a new one? It is a shared feature. Add it to the seam registry in
`docs/specs/workstreams/README.md` first, by team agreement, before using it
in a Stencil stylesheet. Shadow DOM keeps these as the only theme surface;
host apps style by setting these variables on the widget or an ancestor.

## Angular and React consumption

Stencil output targets produce the wrappers. The implementation choice
recorded here covers:

- **Angular wrapper** with CVA configuration for any form-associated widget.
  This is the reason Stencil was chosen over Lit.
- **React wrapper** for `apps/app` and any React host.
- **Raw Custom Elements** as the portable baseline for plain HTML and any
  framework not explicitly wrapped.

Rules:

- Wrappers are generated, not hand-written. Edit the Stencil source, regenerate.
- Angular hosts using raw elements must opt into `CUSTOM_ELEMENTS_SCHEMA`, bind
  non-string values as properties, and listen to the frozen DOM events. The
  generated Angular wrapper is the convenience layer that avoids this manual
  interop and supplies CVA configuration where a widget is a form control.
- React hosts use the generated React wrapper for typed property and custom
  event handling. React 19+ may consume the raw element directly, but that is
  the lower-level portable baseline, not a second widget implementation.
- Wrapper package configuration is owned by the workstream that owns the
  widget source. Do not add package configuration for a widget you do not own.

## SSR boundary

`apps/app` is a Vite SPA. **Phase 1 is client-side only and SSR is out of
scope.** Angular SSR parity is not a documented Stencil output-target
guarantee. Do not claim it, do not design for it, and do not block on it.

If SSR becomes a real requirement later, it is a new decision that must be
recorded the same way this one was: as an explicit delta against the source
specs, agreed by the team. Until then, widgets render in the browser.

## Workstream ownership and frozen seams

Ownership is unchanged from `docs/specs/workstreams/README.md`:

- **Stream 1** owns `packages/sdk/src/capture/**` and exposes
  `<rentgen-scanner>`.
- **Stream 4** owns `client/**`, `config.ts`, `storage/**`, `results/**`,
  `events.ts`, `index.ts`, and `apps/app/**`. It is the integration hub and
  owns every shared wiring file. Streams 1, 2, 3, and 5 never edit
  `config.ts`, `index.ts`, `events.ts`, or `RentgenClient`.
- **Stream 5** owns `packages/sdk/src/upsell/**` and exposes
  `<rentgen-upsell>` and `createAssetAdapter`.

Frozen files change only by team agreement: `types.ts`, `adapters/types.ts`,
`events.ts`, and the seam registry in the workstreams README.

**Pause and coordinate before any shared seam change.** If a task would
require editing a frozen contract, adding or renaming a shared event, tag,
factory signature, or CSS variable, changing the shape of data handed off
between streams, or editing another stream's files, stop. Name the owning
stream and what needs agreeing. Then proceed only on the parts fully inside
your own folder. This rule overrides "just get it done."

## PoC-first implementation order

The Phase 1 → 2 → 3 firewall stays intact. Stencil does not reorder it.

1. **Stub first.** Each stream ships a working stub for its seam before the
   real thing, so downstream is never blocked. `getClient()` already
   defaults to a stub-backed client offline.
2. **Phase 1 — PoC.** One screen, one button, two widgets, one SDK call:
   tap → `getClient().scan(imageBase64)` → `<rentgen-results>` renders item
   cards plus the running total. Build this as Stencil components against
   the frozen tags and events. Demo it cleanly before touching Phase 2.
3. **Phase 2 — live pan.** Only after Phase 1 demos cleanly. Replace
   tap-to-capture with live detection, tracking, and best-in-frame crops.
   Same `getClient().scan()` call, now invoked with a single-object crop.
4. **Phase 3 — product stretch.** `AssetAdapter` report card, cognee
   persistence, upsell. Only if Phase 2 is solid.

Do not start Phase 2 until Phase 1 demos cleanly. Do not start Phase 3 until
Phase 2 is solid.

## Implementation checklist

Use this as a pre-merge and pre-PR gate. Each item must be true.

- [ ] The widget tag is one of `rentgen-scanner`, `rentgen-results`,
      `rentgen-upsell`. No new tag was added.
- [ ] Events used are exactly `scan:start`, `scan:complete`, `scan:error`
      with their frozen payloads. No new event was added.
- [ ] Theme uses only `--rentgen-accent`, `--rentgen-card-bg`,
      `--rentgen-radius`, `--rentgen-font`. No new CSS variable was added.
- [ ] Client API calls go through `getClient().scan()`,
      `getClient().consume()`, or `configureRentgen()`. No new client method
      was added.
- [ ] Factory signatures match `createDetectionAdapter`,
      `createEnrichmentAdapter`, `createAssetAdapter` exactly.
- [ ] The widget self-registers on import and imports no other widget.
- [ ] Cross-widget coordination is via `events.ts` only.
- [ ] No file outside this stream's owned folder was edited, unless agreed
      with the owning stream.
- [ ] No frozen file (`types.ts`, `adapters/types.ts`, `events.ts`, seam
      registry) was edited without team agreement.
- [ ] Shadow DOM is on; theming is via CSS custom properties only.
- [ ] TypeScript strict passes; state updates are immutable.
- [ ] Errors are surfaced via `scan:error`, not swallowed.
- [ ] The SDK does not read `import.meta.env`; host apps pass env values
      into `configureRentgen`.
- [ ] No SSR is claimed or designed for. `apps/app` stays a Vite SPA.
- [ ] Phase 1 demos cleanly before any Phase 2 work begins; Phase 2 before
      Phase 3.
- [ ] Angular and React wrappers are generated by Stencil output targets,
      not hand-written. CVA configuration is used for form-associated
      Angular wrappers.
- [ ] Raw Custom Elements remain consumable from plain HTML.

## Out of scope

- Editing any source spec, frozen contract, or another stream's files.
- Adding or renaming tags, events, CSS variables, factory signatures, or
  package configuration.
- Claiming or designing for Angular SSR parity.
- Backend work of any kind. The project is client-side only.
- Automated tests (deliberate hackathon scope cut; smoke-test on real venue
  objects and keep a recorded fallback video).
- Phase 2 and Phase 3 work before the prior phase demos cleanly.
- Any change to fainin version facts.
