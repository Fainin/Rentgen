Working with Claude Fable 5 in this repo. Distilled from Anthropic's "Prompting Claude Fable 5" guidance. Fable follows brief instructions well and *degrades* under over-prescription — so this file stays short on purpose. The session default model is set to `claude-fable-5` in `.claude/settings.local.json`.

**Effort is the main dial.** `high` is the default; `xhigh` for the hardest, capability-sensitive work; `medium`/`low` for routine mechanical work. Lower effort on Fable still beats higher effort on older models — drop to `low`/`medium` when a task finishes but takes longer than it needs, or when you want a snappier interactive loop. During the hackathon's fast phases, bias toward `medium`.

**Act when you can act.** When you have enough to act, act. Don't re-derive settled facts, re-litigate decisions already made, or narrate options you won't pursue. If weighing a choice, give a recommendation, not a survey. (Applies to user-facing output, not thinking.)

**Do the simplest thing that works.** At higher effort Fable can over-tidy. Don't add features, refactor, or introduce abstractions beyond what the task requires — a bug fix doesn't need surrounding cleanup, a one-shot doesn't need a helper. No speculative future-proofing. Only validate at system boundaries (user input, external APIs); trust internal code and framework guarantees. This matches Rentgen's PoC-first principle and its "no backwards-compat shims" hackathon scope.

**Lead with the outcome.** First sentence of a final summary answers "what happened / what I found" — the TLDR the user would ask for. Detail and reasoning come after. Keep it short by being selective about what to include, not by compressing into fragments, abbreviations, or arrow-chains. A final summary is for a reader who didn't watch the tool calls: complete sentences, spelled-out terms, each file/flag/id in its own plain clause.

**Ground progress claims.** Before reporting progress, check each claim against an actual tool result from this session. Report outcomes faithfully: if typecheck/build fails, say so with the output; if a step was skipped, say that; when something is verified, state it plainly without hedging. Don't claim work you can't point to evidence for.

**Assessment vs. action.** When the user is describing a problem, asking a question, or thinking out loud, the deliverable is your assessment — report findings and stop; don't apply a fix until asked. Before a state-changing command (delete, restart, config edit, `git` history rewrite), confirm the evidence supports that specific action. Respect the workstream scope-discipline in `CLAUDE.md` — pause before touching a frozen contract or another stream's files.

**Delegate freely.** Fable dispatches parallel subagents reliably. Hand independent subtasks (per-workstream exploration, per-file edits, verification) to subagents and keep working while they run; intervene only if one drifts or lacks context. Always set each subagent's `model` explicitly — see [agent-efficiency.md](./agent-efficiency.md).

**Migration note (when adapting older skills/prompts):** prompts written for pre-Fable models are often too prescriptive and can lower Fable's output quality — prune stale instructions rather than piling on. Never instruct Claude to echo, transcribe, or explain its internal reasoning as response text; on Fable that can trip the `reasoning_extraction` safety classifier and force a fallback to Opus. If reasoning visibility is needed, read the structured `thinking` blocks instead.
